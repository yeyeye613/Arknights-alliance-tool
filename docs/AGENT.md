## 3. Architecture Rules

- 按业务领域组织代码，不单纯按照文件类型堆积。
- 界面组件负责展示与交互。
- Composables 负责 Vue 响应式状态及界面协调。
- Domain 负责独立的业务规则和计算。
- Infrastructure 负责存储、文件读写和外部环境交互。
- Shared 只放真正通用的功能。

模块之间通过明确的数据接口协作。

禁止：
- 随意访问其他模块的内部状态。
- 在多个模块重复实现相同业务规则。
- 将纯计算逻辑绑定到 Vue 组件。
- 为简单功能引入不必要的设计模式和抽象层。
- 为了符合目录结构而机械拆分文件。

具体模块边界以 architecture/module-map.md 为准。

## 4. Code Modification Rules

修改代码前：

1. 定位相关模块和入口文件。
2. 阅读相关实现及调用关系。
3. 检查已有测试。
4. 确认修改是否影响其他模块。

修改过程中：

- 优先复用现有实现。
- 保持修改范围与任务目标一致。
- 不随意重写已经正常工作的模块。
- 不擅自改变现有业务规则。
- 不删除无法理解的代码来解决问题。
- 不引入没有必要的依赖。
- 不伪造测试结果。

行为规则:
-  不要假设。不要隐藏困惑。主动暴露权衡取舍。
-  只写解决当前问题的最小代码，不做任何推测性功能。 
-  只修改必须改的地方，只清理自己产生的问题。
- 明确定义成功标准，验证通过前持续迭代。

反过度工程/反防御性编程
- 信任内部代码和框架保证。
- 只在系统边界（用户输入、外部API、网络）做校验。
- 禁止为「不可能发生」的场景添加错误处理、回退、空值检查或验证。
- 绝不吞掉错误（禁止rescuenil/宽泛catch静默默认值）。
- 禁止为一次性操作创建辅助函数、工具类或抽象。
- 优先快速失败，而不是掩盖问题。
- 涉及架构调整时，先说明改动范围、原因和兼容性风险。

## 5. Testing and Verification

根据修改范围执行相应验证：

- 单元测试：验证独立业务规则。
- 集成测试：验证跨模块协作。
- 类型检查：验证数据接口。
- 生产构建：验证项目可正常构建。

修改完成后：

1. 只在系统边界做校验
2. 执行必要的全量检查。`frontend/` 下至少跑一次 `npm run verify`（类型 + lint + 测试 + 死代码），
   改动涉及构建配置时再跑 `npm run build`。
3. 检查 git diff。
4. 检查是否存在无关修改。
5. 汇报实际执行的命令和结果。

如果测试无法执行，明确说明原因，不得声称通过。

具体命令以 package.json 为准。

## 6. Documentation Rules

文档只维护重要且具有长期价值的信息，不重复记录代码中已经明确表达的细节。

以下情况需要同步更新文档：

- 新增或删除业务模块。
- 改变模块职责或依赖关系。
- 修改核心数据结构。
- 修改重要业务规则。
- 改变项目安装、运行或构建方式。

普通 UI 样式调整、局部 Bug 修复和内部实现优化通常不需要更新架构文档。

文档必须与实际实现一致。

不要为了完成文档更新而编造尚未实现的功能。
