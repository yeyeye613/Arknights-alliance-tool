## 3. Architecture Rules

- 按业务领域组织代码，不单纯按照文件类型堆积。
- 界面组件负责展示与交互。
- Composables 负责 Vue 响应式状态及界面协调。
- Domain 负责独立的业务规则和计算。
- Infrastructure 负责存储、文件读写和外部环境交互。
- Shared 只放真正通用的功能。

模块之间通过明确的数据接口协作。

禁止：
- 随意访问其他模块的内部状态。
- 在多个模块重复实现相同业务规则。
- 将纯计算逻辑绑定到 Vue 组件。
- 为简单功能引入不必要的设计模式和抽象层。
- 为了符合目录结构而机械拆分文件。

具体模块边界以 docs/architecture/module-map.md 为准。

## 4. Code Modification Rules

修改代码前：

1. 定位相关模块和入口文件。
2. 阅读相关实现及调用关系。
3. 检查已有测试。
4. 确认修改是否影响其他模块。

修改过程中：

- 优先复用现有实现。
- 保持修改范围与任务目标一致。
- 不随意重写已经正常工作的模块。
- 不擅自改变现有业务规则。
- 不删除无法理解的代码来解决问题。
- 不引入没有必要的依赖。
- 不伪造测试结果。

行为规则：

- 不要假设。不要隐藏困惑，主动说明不确定性和设计取舍。
- 只写解决当前问题所需的最小代码，不添加推测性功能。
- 只修改必要的地方，只清理本次修改产生的问题。
- 明确成功标准，并根据实际结果验证。
- 遇到无法解决的验证失败，说明原因和已尝试的处理，不要通过无关修改掩盖问题。

反过度工程与反防御性编程：

- 信任内部代码和框架保证。
- 只在系统边界（用户输入、外部 API、网络）做必要校验。
- 不为不可能发生的场景添加错误处理、回退、空值检查或验证。
- 不吞掉错误，禁止静默捕获异常并返回默认值。
- 不为一次性操作创建辅助函数、工具类或抽象。
- 优先快速失败，而不是掩盖问题。
- 涉及架构调整时，先说明改动范围、原因和兼容性风险。

## 5. Testing and Verification

根据修改范围执行相应验证：

- 单元测试：验证独立业务规则。
- 集成测试：验证跨模块协作。
- 类型检查：验证数据接口。
- 生产构建：验证项目可正常构建。

修改完成后：

1. 确认修改范围和预期行为。
2. 执行必要的检查。frontend/ 下至少运行一次 `npm run verify`（类型检查、lint、测试、死代码检查）。
3. 改动涉及构建配置、依赖导入或构建行为时，额外运行 `npm run build`。
4. 检查 git diff。
5. 检查是否存在无关修改。
6. 汇报实际执行的命令和结果。

如果测试无法执行，明确说明原因，不得声称通过。

具体命令以 package.json 为准。

## 6. Documentation Rules

文档只维护对使用、开发和长期维护有价值的信息，不重复记录代码中已经明确表达的细节。

文档更新时：

- 先检查现有文档及相关代码，确认内容是否过期、重复或缺失。
- 根据文档职责选择修改位置，不随意将所有信息集中到一份文档。
- 技术规则必须有实际代码、配置或测试依据。
- 不记录没有长期价值的一次性开发过程和排障细节。
- 不为了体现本次工作而修改无关文档。
- 不重复维护已经在其他文档中明确说明的信息。
- 不得将规划中的功能描述为已经实现。

文档职责：

- README.md：项目介绍、功能、安装、运行和使用说明。
- CONTRIBUTING.md：开发环境、运行方式、代码检查、项目约定和贡献流程。
- AGENTS.md：AI 开发约束、仓库操作规则及文档索引。
- CHANGELOG.md：对外发布版本的更新记录。
- docs/architecture/：模块职责、数据结构、依赖关系和重要设计决策。
- SECURITY.md：安全问题报告与处理方式。
- THIRD-PARTY.md：第三方数据与图像的来源、权利人及许可状态。新增或替换素材时同步。

以下情况需要同步更新相关文档：

- 新增或删除业务模块。
- 改变模块职责或依赖关系。
- 修改核心数据结构。
- 修改重要业务规则。
- 改变项目安装、运行或构建方式。

普通 UI 样式调整、局部 Bug 修复和内部实现优化通常不需要更新架构文档。

### Documentation Writing Style

- 使用简洁、准确、客观的技术表达。
- 优先说明规则、事实和必要原因。
- 避免口语化、说教式表达、口号式总结和主观评价。
- 避免过度使用加粗、警告和强调语句。
- 不重复解释常见工具的基础原理。
- 不为填充章节而添加没有实际价值的内容。
- 不将个人经验、一次性任务背景或开发过程写成长期规范。
- 特殊故障和环境问题仅在仍具有实际维护价值时保留，并放在合适的位置。
- 不为了精简而删除有实际维护价值的技术细节。

## 7. Git and Commit Rules

### Commit Principles

Commit 用于记录项目代码的逻辑变更，不用于汇报任务执行过程。

一次提交应围绕一个逻辑完整的变更，尽可能保持独立和可回退。

- 不混合无关功能、重构、Bug 修复和文档修改。
- 不按文件数量机械拆分提交。
- 不将多个无关小改动合并成一个大型提交。
- 不为了增加提交数量而拆分存在强依赖的修改。
- 不提交与当前任务无关的文件或已有用户修改。

### Commit Message

使用 Conventional Commits 格式：

`type(scope): description`

常用 type：

| type | 用途 |
| --- | --- |
| feat | 新增用户可感知的功能 |
| fix | 修复错误行为 |
| refactor | 不改变外部行为的结构调整 |
| docs | 文档修改 |
| test | 测试修改 |
| style | 不影响功能的格式调整 |
| chore | 依赖、脚本、构建及其他维护工作 |

要求：

- 标题简洁描述实际变更及其结果。
- scope 优先使用项目现有模块名。
- 避免使用「继续优化」「进一步完善」「第二轮修改」等过程性表达。
- 不在标题中写任务背景、工作过程或完成情况。
- 正文只补充 diff 无法直接体现的重要设计原因、兼容性影响和必要约束。
- 没有必要补充的信息时，不写正文。
- 不重复列举 diff 已经能够清楚展示的文件和代码改动。
- 保持仓库现有语言风格，避免为了形式统一而强行翻译已有术语。

### Git Operation

修改前：

- 检查 `git status`，确认工作区现状。
- 区分本次任务修改和已有未提交修改。

提交前：

- 检查完整 diff 和暂存区。
- 确认每个提交的文件和变更属于同一逻辑意图。
- 不擅自将用户已有修改纳入提交。

涉及分支、合并、变基、撤销历史等操作时：

- 优先保护已有提交和用户未提交的修改。
- 不擅自执行可能丢失工作内容的操作。
- 不擅自 amend、reset --hard 或 force push。
- 无法确定操作影响时，先说明风险并请求确认。

## 8. Version and Release Rules

项目版本遵循 Semantic Versioning（MAJOR.MINOR.PATCH）。

- MAJOR：存在不兼容的重大变更。
- MINOR：新增向后兼容的功能。
- PATCH：向后兼容的问题修复。

版本管理要求：

- 日常 Commit 不需要创建 Tag。
- 只有达到明确发布条件的稳定版本才创建版本 Tag。
- Git Tag、package.json 中的项目版本及 GitHub Release 应保持一致（适用时）。
- CHANGELOG 记录对外发布版本的实际变化。
- 不因为完成一次开发任务就自动升级版本号。
- 不擅自创建、删除或移动已发布的版本 Tag。
- 发布前检查工作区、测试结果、版本号和更新记录。

版本发布由用户确认后执行，除非用户明确授权自动发布。

## 9. Delivery

任务完成后，简要说明：

- 实际修改了什么。
- 重要设计决策及其原因。
- 执行了哪些验证及其结果。
- 尚未解决的问题和需要用户确认的事项。

只报告实际完成的工作，不将计划、推测或未验证结果描述为已完成。
